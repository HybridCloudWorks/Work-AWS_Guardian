# Cedar-first safety story is modeled offline but not yet enforced on the production path

This session built the Continuous Compliance Guardian POC from an empty repo: offline Python domain (discovery, authz, policy activation, reconciliation, tools, API, audit, observability), a Next.js console shell, and Terraform for storage, IAM boundaries, and a feature-flagged AgentCore Gateway + Policy Engine. The design's central promise is Cedar-first authorization — forbids override permits, no matching permit denies, and only an audited activation flips a versioned permit set to allow. That promise is fully realized in the *test double* (`InMemoryCedarGateway`) and the shared `authz` model, and the offline demo proves the `deny -> activate -> allow -> reconcile` sequence end to end. The production adapter, the metric catalog, and the reconcile-resolution gate are thinner than the doubles they stand in for, and the Terraform binds the engine in `LOG_ONLY`, which by AWS's own definition logs but does not enforce.

Watch for: the production `AgentCoreGatewayClient` performs no local checks and forwards blindly to a transport, while the deployed Policy Engine is bound `LOG_ONLY` — a deployment window where a permit that should deny is only logged, not blocked (confirmed). Idempotency and replay protection exist only in the test double, not on the production path (confirmed). The `Metric` catalog the threat model cites as its runtime detection layer is never emitted by any production component (confirmed). `confirm_from_discovery` resolves a finding on a bare `drift_still_present=False` boolean with no evidence binding (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The authorization ordering is correct where it is implemented, but "where it is implemented" is the whole concern. `authz.py` and `InMemoryCedarGateway` enforce forbid-overrides-permit and default-deny; the real `AgentCoreGatewayClient` is a pass-through with a docstring saying authorization belongs to the remote Gateway. The Terraform then binds that remote engine in `LOG_ONLY`. So on the deployed path there is currently no enforcement at either end: the client doesn't check, and the engine only logs. The spec calls for the Gateway to enforce deny in enforce mode; the deploy gate deliberately chooses `LOG_ONLY` for schema capture, which is defensible for capture but means the "deny" half of the safety story is unproven against anything real. The forbids are the same story — they only deny in the double, not in a `LOG_ONLY` engine.

Idempotency lives entirely in the double, keyed on `idempotency_key` with no binding to the request payload, and it caches terminal failures as replayable results. The production client has no idempotency at all. A real deployment would either double-execute (no dedupe) or, if the double's logic were ported as-is, replay a stale success for a mutated payload and permanently cache a transient failure.

The metric catalog is a well-designed, stable enum — but no production module imports it. The threat model maps eight threats to specific metrics as their detection control; today those metrics fire only inside unit tests. Detection is aspirational, not wired.

Reconciliation is the one lifecycle authority and its transition allow-list is sound, but the resolve gate trusts a caller-supplied boolean instead of a discovery-run correlation or evidence reference, so nothing structurally prevents a finding being resolved without a real confirming read.

The IAM action-name fix and the `ReconcileContext` refactor are both clean and behavior-preserving. No regression found in either.

### The enforcement gap: pass-through client + LOG_ONLY engine

The design names the Gateway/Cedar boundary (B4) as the one component that "authorizes every mutation" and must "not be bypassed by any direct path." The offline model honors this: `authz.evaluate` applies forbids first, denies when the permit set is inactive, and allows only on an explicit active permit; `InMemoryCedarGateway` calls straight into it and refuses to touch a tool handler on a deny. `ComplianceApi` never makes a local allow/deny decision — it resolves the target ARN server-side from the stored finding (closing the T1/T2 confused-deputy and forged-context vectors at the API layer) and delegates to the gateway port. That part is well built.

The production adapter is where the story thins out:

```python
class AgentCoreGatewayClient(GatewayInvocationPort):
    def __init__(self, transport):
        self._transport = transport
    def invoke(self, request):
        return self._transport.invoke(request)
```

No forbid evaluation, no default-deny, no audit — by design, because "authorization belongs to the remote Gateway Policy Engine." That is architecturally correct *only if* the remote engine actually enforces. The Terraform binds it as:

```hcl
policy_engine_configuration {
  arn  = aws_bedrockagentcore_policy_engine.this[0].policy_engine_arn
  mode = "LOG_ONLY"
}
```

AWS defines `LOG_ONLY` as evaluating the policy and logging the decision without enforcing it. So on the deployed path the client doesn't check and the engine doesn't block. The module comment claims "the always-on forbids still evaluate, but no permit is enforced." That conflates two things: in `LOG_ONLY` the forbids evaluate but their *deny is not enforced* either. A caller that reaches the Gateway with a `disable_cloudtrail` request or a prod target would be logged and allowed through to the target, because nothing downstream re-blocks it — the tool Lambda's own safety recheck is the only backstop, and that is a defense-in-depth layer, not the authorization boundary (confirmed against the module and the AWS mode semantics).

To answer the question directly: **yes, there is a window.** When `enable_gateway=true` and a permit set later exists, any request in `LOG_ONLY` is allowed regardless of whether Cedar would deny it. The `deny -> activate -> allow` transition is real today *only* in the double, and only because the demo manually calls `gateway.activate_permits(...)` to bridge control-plane activation to the enforcement point. In AWS that bridge is the enforce-mode flip, which this Terraform never performs and which the deploy gate explicitly defers. For the schema-capture step the threat model scopes (CCGDemo-tagged targets, no permits activated), `LOG_ONLY` is a reasonable choice — but the design's stated invariant ("the Gateway enforces deny for calls with no active permit", "all mutation requests must traverse the Gateway Policy Engine in enforce mode") is not met by anything deployable in this session's work. The gap is documented as residual risk T2, but the enforcement-mode consequence (deny is not enforced, not just permits) is understated in the module comment.

```
offline (tested):   API --> InMemoryCedarGateway --> authz.evaluate  [DENY enforced]
production (built):  API --> AgentCoreGatewayClient --> transport --> Gateway(LOG_ONLY)  [decision logged, not enforced]
```

### Idempotency and replay: guarantee lives only in the double

The design's tool contract promises idempotent operations and the threat model's T3 (replay) leans on "idempotency key on remediation (second call is a no-op replay)." That guarantee is implemented only in `InMemoryCedarGateway`:

```python
if request.idempotency_key in self._replays:
    replay = replace(self._replays[request.idempotency_key], idempotency_replayed=True)
    return InvocationResult(decision=decision, tool_result=replay)
...
self._replays[request.idempotency_key] = result
```

Two behaviors a real deployment would inherit if this logic were the model:

The replay key is `idempotency_key` alone, with no binding to the request payload. A caller (or a retry layer) that reuses a key with different `parameters` gets the *prior* result back and the new mutation silently never runs. The double can't detect this because it stores only the result, not a hash of what produced it.

The cache is populated unconditionally, including the synthesized `FAILED` result from the `except` branch. A transient tool failure (throttle, timeout) is therefore cached as terminal: every retry with the same key replays the failure instead of re-attempting. That contradicts the tool contract's "uncertain result pauses for reconciliation" — here an uncertain result is frozen as a permanent failure keyed to that request.

And the production `AgentCoreGatewayClient` has *none* of this — it forwards every call. So the real path today has the opposite failure mode: no dedupe at all, so redelivery double-executes. Whichever way it is eventually resolved, the replay-safety property is currently unproven on the production path and subtly wrong in the double.

### Observability: the detection layer is defined but never fires

`observability.py` is a clean, stable metric catalog with a `MetricSink` seam and null/in-memory implementations. The threat model treats these metrics as the *runtime detection control* for every threat: T1/T2 point at `ccg.gateway.deny`, T3 at `ccg.tool.noop` and `ccg.policy.activation_rejected`, T5/T7 at `ccg.audit.write_failure`, T8 at `ccg.discovery.partial`/`failure`, and so on.

No production module imports `observability`. A search across `discovery`, `gateway`, `policy`, `reconcile`, `api`, `tools`, `sources`, `audit`, `voice`, and `http` finds zero references — the only `.increment`/`Metric.` usages are in the module itself and in `test_observability.py`. So every metric fires exactly zero times outside unit tests. The threat model's detection column is describing metrics that do not yet exist at runtime. This is not a correctness bug in the catalog — it is a soundness gap in the threat model's reliance on it: a reviewer reading the mitigation table would reasonably believe `ccg.gateway.deny` alarms on a denied mutation, when nothing emits it. Either the sinks get wired through the components that produce these events, or the threat model should mark the metric column ⏳ like the other deploy-time items.

### Reconcile resolution: a boolean where evidence belongs

`ReconciliationService`'s transition allow-list structurally enforces "a tool reporting success does not mean the drift is fixed" — tool outcomes never move a finding straight to `RESOLVED`, and only `SUCCEEDED`/`NOOP` are resolvable (matches CCG-REQ-026, ACC-14). The gap is the resolve trigger:

```python
def confirm_from_discovery(self, finding_id, context, *, drift_still_present: bool) -> Finding:
    ...
    if drift_still_present:
        return finding
    if finding.status not in _RESOLVABLE_FROM:
        return finding
    return self._transition(finding_id, FindingStatus.RESOLVED, ...)
```

`drift_still_present` is a bare boolean supplied by the caller. Nothing binds it to an actual discovery run: no run/correlation ID for the confirming read, no evidence reference, no check that the read was a *complete* run rather than a partial or failed one. The docstring says resolution happens because "a clean read confirms it," but the method has no way to know a clean read occurred — it trusts the caller's `False`. In the demo the caller is honest (it runs an empty discovery pass, then passes `False`), but the honesty lives in the demo wiring, not in the service. A caller that passes `drift_still_present=False` off the back of a throttled or partial discovery read would resolve the finding — exactly the T8 vector ("a partial/failed read is treated as compliant") that the design says must never happen. So: **yes, a finding can reach RESOLVED without a real confirming read**, as far as the service's own contract is concerned. The fix is to pass the discovery-run correlation ID (or an evidence ref) and have the service validate it came from a completed, non-partial run whose result set genuinely omits this finding.

### IAM action-name fix and ReconcileContext refactor: clean, no regression

The IAM fix (PR #7) replaces non-existent `UpdateGatewayPolicy`/`GetGatewayPolicy`/`ListGatewayPolicies` with the real `UpdatePolicy`/`GetPolicy`/`GetPolicySummary`/`ListPolicySummaries` and re-scopes from `gateway/*` to `policy/*` and `policy-engine/*`. The control-plane role still carries no remediation actions and the deny boundary is untouched, so this tightens correctness without widening privilege. Worth calling out as a good catch — a policy referencing phantom actions would have failed closed at deploy in a confusing way.

The `ReconcileContext` refactor (commit 09be81b) bundles `actor`/`correlation_id`/`request_id` into one frozen dataclass and threads it through the three lifecycle methods. It is purely mechanical: the same three values reach the same audit fields via `_transition`, and the suite still passes. One incidental improvement — the old `confirm_from_discovery` had `actor: str = "discovery-agent"` as a default while other args were required; the refactor makes the context mandatory and explicit, removing a spot where a caller could silently omit the actor. No behavioral regression in either change.
